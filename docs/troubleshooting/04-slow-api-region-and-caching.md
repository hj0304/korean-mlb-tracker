# 04. 첫 로딩이 느림(~2s + 가끔 11s) — 리전 간 거리 + 캐시 부재

## 증상
- 페이지 첫 로딩이 답답함. 가끔 훨씬 더 느림.

## 원인
두 가지가 겹침:
1. **리전 간 거리**: 백엔드(Northflank **US Central**) ↔ DB(Supabase **Seoul**) ↔ 사용자(한국).
   모든 요청이 태평양을 왕복 → DB 붙는 요청마다 ~1s 추가, 콜드 커넥션 시 TLS 핸드셰이크로 ~11s 스파이크.
2. **캐시 부재**: 데이터는 하루 1번 ETL로만 바뀌는데 **매 요청 DB를 침**.

## 진단
응답 시간을 엔드포인트별로 측정:
| 엔드포인트 | 시간 |
|---|---|
| `/health` (DB 안 씀) | ~0.6s ← 순수 네트워크 기저값 |
| `/players` (DB) | ~1.6s, 가끔 11s |
| `/players/{id}` | ~1.8s |

→ `/health`(0.6s)와 DB 엔드포인트(~1.8s)의 **차이 ~1s가 DB 왕복 비용**. 쿼리는 단순(14행)이라 쿼리 복잡도가 아니라 **거리**가 원인.

## 해결
- **인프로세스 TTL 캐시(5분)** + `Cache-Control` 헤더 (읽기 전용 + 일 1회 갱신이라 안전).
  → 첫 요청만 DB, 이후 모든 사용자에게 ~0.6s. 스파이크 제거. **~2s → ~0.6s**.
- **리전 이전은 포기**: Northflank 무과금은 US Central / UK뿐(아시아=유료). 게다가 둘 중 **US Central이 한국·Seoul DB 모두에 더 가까움**(UK가 더 느림) → 이미 무과금 최선이라 건드리지 않음.

## 교훈
- 느림을 추측하지 말고 **측정**부터. `/health`처럼 DB 없는 엔드포인트를 **기저값**으로 두면 "네트워크 vs DB vs 쿼리"가 분리된다.
- **데이터 변경 주기가 길수록 캐시가 강력**하다. 일 1회 갱신이면 5분 캐시의 staleness는 무의미.
- 무과금 제약에선 못 고치는 부분(사용자→US 0.2s)을 인정하고, **고칠 수 있는 부분(DB 왕복)에 집중**.
